# 2026-07-20

## audio-core 能力盘点与缺口分析

用户提问：作为音频核心给移动端/PC 端提供底层音乐播放能力，还缺什么。

### 关键发现
- **网络流媒体是致命缺口**：`Decoder::start(path)` 只接受本地文件 Path，没有 HTTP/HLS/ICY 流式播放能力。Symphonia 的 MediaSourceStream 接受任意 Read+Seek，可包装 Range 请求的 HTTP 源补齐。
- **engine/output 完全绑死 cpal**：`lib.rs` 中 engine 和 output 模块都在 `#[cfg(feature = "cpal-backend")]` 后面。移动端若用 oboe-rs / AVAudioEngine，需要重新实现一套 engine，consumer.rs 已解耦但 engine 未解耦。
- **设备枚举 API 未 pub**：`output_cpal.rs::list_device_names()` 是 `pub(crate)`，SDK 层拿不到设备列表。
- **移动端集成缺失**：iOS AVAudioSession 类别管理、Android 音频焦点、后台播放、锁屏 Now Playing 都没有 hook。
- **播放控制基本款不全**：无 prev_track、无跳到队列指定位置、无 A-B 循环、无播放速度/变速变调（rubato 已在用可补）、无淡出停止。
- **元数据薄**：只有 title/artist/album/duration/cover，缺 genre/year/track_no/composer/lyrics、bitrate/sample_rate/bits_per_sample/codec。
- **无歌词**：LRC 内嵌/外挂解析、时间轴同步全缺。
- **格式缺口**：APE/TTA/Musepack/CUE Sheet（整轨分曲）缺；无任何编码能力。
- **持久化缺失**：上次播放位置、播放队列、播放模式都没保存。
- **资源/健壮性**：seek 期间 ready_rx 阻塞 3s 等待；长队列预加载无 LRU；消费者 panic 后引擎状态可能不一致。

### 评估语气
按用户偏好，致命缺口直说，nice-to-have 标注优先级，不堆好话。

## 修正：网络层应放客户端，不要进 audio-core

用户反问"网络不能放在客户端做吗"——戳到我盲点。原建议（audio-core 内部加 HTTP Range 源 + reqwest）是过度设计。

**正确的修复方向**：
- 当前 `Decoder::start(path: &Path)` 把"客户端自己拉网络再喂进来"这条路也堵死了
- 应新增 `Decoder::start_with_source(src: Box<dyn ReadSeek>, ...)` 接口，接受任意 Read+Seek 数据源
- 客户端用自己的网络栈（OkHttp/URLSession/fetch）拉数据，实现 Read+Seek adapter 传入
- audio-core 保持纯 Rust 零网络依赖，符合 Symphonia 的 MediaSourceStream 设计哲学

**为什么放客户端更好**：
- 鉴权 / CDN 调度 / 证书 pinning / 弱网重连 / 统计埋点 都是客户端业务，audio-core 没法覆盖
- 移动端已有成熟网络栈，不重复造轮子
- audio-core 不引入 HTTP 依赖，二进制体积和编译目标保持干净

**对上一轮"致命缺口"清单的修正**：
- "HTTP/HTTPS 流式播放"这个缺口的本质不是"audio-core 没有网络代码"，而是"audio-core 接口不接受外部数据源"
- 修复成本从"加 HTTP 库 + Range 源实现"降到"新增一个接受 trait object 的接口"——更低
- iOS AVAudioSession / Android 音频焦点 / engine 后端解耦 仍然是致命缺口，不变
